## 0. 结论速览（TL;DR）

| 问题 | 结论 |
|---|---|
| **崩溃偏移是否"穷尽"？** | **没有，而且在原理上不可能穷尽。** 全库仅 **57 条**（Game.dll 51 条），只覆盖 **5 个版本**；其中至少 **3 条是占位符假数据**。真实覆盖率 < 1%。 |
| **比"覆盖不足"更严重的问题** | 知识库把 **三种不同地址空间混在一起**（绝对 VA / 模块 RVA / 节:偏移），加上"后 5 位后缀模糊匹配"，会产生**看似确定、实则错误**的诊断——这比"未知"更有害。 |
| **客户端 / 服务端知识库已分裂** | `core/knowledge.py` 与 `server/app.py` 各维护一份，**同一诊断的 RVA 已漂移**（如 0x00046394 vs 0x00045394），且服务端含 10 位十六进制、绝对地址等脏数据。 |
| **DMP 分支根本不查知识库** | `auditor.py` 里 DMP 算出 `Game.dll+0X46394` 后只打印不查表，导致这条**本来能命中**（0x00046394 闪电崩溃）的记录变成空白——history.db 里可实证。 |
| **上报链路是断的** | `core/reporter.py:80` 用 4 个变量解包 5 元组 → 每份日志都抛 `ValueError`，被 `except` 吞掉。云端聚合等于没跑。 |
| **正确范式** | 从「**白名单查表**」转向「**符号化 + 栈回溯 + 指纹聚类**」。知识库从"唯一真相"降级为"已知案例缓存"。 |

## 2. 核心问题一：崩溃偏移知识库远未穷尽

### 2.1 数据事实

```
Game.dll   1.24e    27 条   ← 占全库 47%，明显是"某一版重点攻坚"的遗留
Game.dll   1.26a     6 条
Game.dll   1.27a    13 条
Game.dll   1.28.5    2 条
Game.dll   1.31.1    3 条
WorldEditKKWE.exe    4 条
Storm.dll            2 条
────────────────────────
合计                57 条
```

### 2.2 三条以上是"假数据"

```python
"0x00456789": "单位路径搜索逻辑崩溃..."
"0x00123456": "渲染引擎溢出..."
"0x00789ABC": "同步错误导致的内存违例..."
```

`456789 / 123456 / 789ABC` 是典型的**键盘顺序占位符**，不可能是真实 RVA。它们至今仍在库中，并且会被当作"已知崩溃"输出给用户。**这是可信度问题，不是覆盖率问题。**

### 2.3 版本覆盖缺口

魔兽 III 的公开版本至少有：

```
1.20e / 1.21b / 1.22 / 1.23 / 1.24b / 1.24d / 1.24e / 1.25b / 1.26a
1.27a / 1.27b / 1.28.0 ~ 1.28.7 / 1.29 / 1.30 / 1.31.1
1.32 ~ 1.36（Reforged）/ 2.0
```

库中覆盖 **5 个**。国内 RPG 生态实际主力是 **1.24e、1.27a、1.27b**——1.27b 一条都没有；而 1.27a 与 1.27b 的 Game.dll 是**不同二进制**，RVA 不能互用。

### 2.4 缺失的模块

崩溃帧绝大多数不落在 Game.dll 的"业务逻辑"里，而是：

| 模块 | 现状 | 后果 |
|---|---|---|
| `war3.exe` / `Warcraft III.exe` | **完全缺失** | 启动期、渲染初始化、UI 主循环崩溃无法归因 |
| `mss32.dll`（音频） | 缺失 | 音频崩溃一律"未知" |
| `d3d9.dll` / 显卡驱动 | 缺失 | 玩家侧崩溃被误判为地图问题 |
| `Storm.dll` | 2 条 | 加密地图读取失败无法区分 |
| `WorldEdit*` | 4 条 | 编辑器崩溃覆盖极薄 |

### 2.5 为什么"穷尽偏移"在原理上做不到

这是本次诊断最重要的判断，需要说清楚：

1. **崩溃是"指令级"事件，不是"函数级"事件。** Game.dll 的 `.text` 段是**数十万到百万级指令**，其中任何一条解引用指令（`mov eax,[ecx+8]`、`call [eax]`）在指针为 0 或已释放时都会 0xC0000005。理论上"可能的崩溃点"数量 = 间接访存指令数量，量级在 **10⁴~10⁵**。
2. **RVA 随版本/编译漂移。** 同一 bug 在 1.24e 与 1.27a 的 RVA 毫无关系；1.27a 与 1.27b 也不同。每加一个版本，表的维护成本线性增长。
3. **同一 RVA 可对应多种根因。** 例如 `RemoveLocation` 内部崩，可能是传了 null、可能是句柄已释放、可能是堆被踩坏（崩在"受害者"而非"凶手"处）。**崩溃点 ≠ 病因**。
4. **同一 bug 可崩在不同 RVA。** 堆破坏类问题（越界写、double free）崩溃点每次都不一样，靠查表永远查不到。

**所以：57 条 / 10⁴~10⁵ 个候选点 ≈ 覆盖率 0.05%~0.5%。** 继续"人工往表里加条目"是线性投入、指数缺口，不可持续。

### 2.6 正确的目标应该是什么

| 旧目标（不可达） | 新目标（可达且有用） |
|---|---|
| 让每个偏移都能查到中文解释 | 让**任何**偏移都能给出：`模块 + 函数 + 调用栈 + 疑似 JASS 函数 + 可疑代码行` |
| 人工维护 500 条 | 机器生成符号表 + 社区只贡献"案例注解" |
| 命中即结论 | 命中=高置信度案例；未命中=自动归因+待聚类 |

## 3. 核心问题二：地址空间混乱导致"自信的错误"

这是比覆盖率更危险的缺陷。

### 3.1 三种地址空间被混为一谈

真实世界里的崩溃地址有三种形态：

| 形态 | 示例 | 含义 |
|---|---|---|
| 绝对 VA | `0x6F50A568` | 运行时虚拟地址（旧版 Game.dll 固定加载在 0x6F000000） |
| 模块 RVA | `0x0050A568` | 相对模块基址的偏移，**唯一可跨机器比较** |
| 节:偏移 | `0001:0000A568` | crash.txt 里的 `Logical addr`，与基址无关 |

而 `knowledge.py` 里：

- `"0x00456789"`、`"0x0050A568"` → 看着像 RVA
- `server/app.py` 里 `"0x6F4790C1"`、`"0x631A97CC"` → 明显是**绝对 VA**，却和 RVA 放在同一个 dict 里
- `"0x00086CA030"` → **10 位十六进制**，超出 32 位地址空间，纯脏数据

同一个 `dict` 里放三种语义的 key，查表命中就是运气。

### 3.2 `+0x1000` 是硬编码猜的

```python
# core/auditor.py:307
if section == "0001":
    rva = int(inner_offset, 16) + 0x1000   # ← 假设 .text 的 RVA 恒为 0x1000
else:
    relative_offset = "0x" + inner_offset.upper()   # ← 其他节直接用偏移，错
```

`Logical addr` 是 **PE 节表第 N 节的偏移**。正确做法是读目标模块的 PE 节表：`RVA = Section[N-1].VirtualAddress + offset`。硬编码 `+0x1000` 对 `.text` 恰好成立，对其他节（`.rdata` / `.data`）则完全错位——而**虚表调用崩溃恰恰常落在 `.rdata` 指向的数据段**。

### 3.3 "后 5 位后缀匹配"是误诊制造机

```python
# core/auditor.py:380-391
suffix = search_target[-5:]
for ver, ver_data in game_data.items():        # ← 遍历所有版本
    for off, desc in ver_data['offsets'].items():
        if off.endswith(suffix):               # ← 跨版本模糊命中
            analysis_text = f"[Game.dll ({ver}) 疑似匹配] {desc}"
```

问题：
- 会把 **1.24e 的结论**套到 **1.27a 的崩溃**上；
- 5 位十六进制只有 104 万种组合，57 条表项 × 任意偏移 → 误命中概率虽低但**一旦命中就是高置信度的错误结论**；
- 代码里没有任何"版本必须先确认"的前置校验。

### 3.4 DMP 分支从不查知识库（可实证）

```python
# core/auditor.py:496-499
offset = hex(target_addr - mod['base']).upper()
self.log(f"[+] 崩溃发生于模块: {crash_mod} (相对偏移: {offset})")
analysis_summary += f"[{crash_mod}+{offset}] "     # ← 只拼接，不查表
```

`history.db` 中的真实记录：

| 日志 | 记录的分析结果 | 真相 |
|---|---|---|
| `2026-11-04 12.33.27 Crash.txt` | `[Game.dll+0X50B568] [Game.dll (1.27a)] 移除英雄属性崩溃...` | 文本日志路径命中了，OK |
| `2026-10-12 23.11.12 Crash.txt` | `[Game.dll+0X46394] ` ← **后面什么都没有** | 0x46394 **就是**库里的 `0x00046394`（1.27a 闪电效果崩溃），只因格式是 `0X46394`（大写前缀、无零填充）而漏配 |

**这是全项目最典型的"就差一行代码"的损失。**

### 3.5 顺带发现：版本信息被读出来又扔掉

```python
# engine/dmp_parser.py:84
base, size, _, _, name_rva = struct.unpack('<QIIII', m_data[:24])
#                ↑ TimeDateStamp —— MINIDUMP_MODULE 里有，但被丢弃
```

`TimeDateStamp` + `SizeOfImage` 是**二进制指纹**，可以 100% 确定"这是 1.27a 还是 1.27b 的 Game.dll"，根本不需要用户手选版本。现在这个字段读出来就丢了。

## 4. 核心问题三：工程性缺陷（可直接修）

### 4.1 上报链路必崩（P0）

```python
# core/reporter.py:80
addr, rel_offset, analysis, log_map_name = self.silent_auditor.get_analysis_data(log_content)
# get_analysis_data 实际返回 5 个值：addr, relative_offset, analysis_text, map_name, module_name
# → ValueError: too many values to unpack
```

被外层 `except Exception as e: self.log(f"[-] ... 发生错误: {e}")` 吞掉，表现为"每份日志都上报失败"，但用户只看到一行失败日志。**云端聚合数据实际是空的。**

| 闪电/单位选择 | `0x00046394` | `0x00045394` |

同一崩溃在本地诊断和云端统计里会得到**不同结论**。而且服务端的 key 是 `"0x6F000000"` / `"0x6F000002"` 这种**伪基址**，与客户端结构完全不兼容。

### P1 — 版本指纹与符号化（1~2 周，核心价值）

```
① 版本指纹
   MINIDUMP_MODULE.TimeDateStamp + SizeOfImage  →  sha1(f"{tds}:{size}")
   建立 map: fingerprint → "Game.dll 1.27a"
   → 彻底消灭"用户选错版本导致误诊"

② 栈回溯
   换用 skelsec/minidump，读 ThreadListStream + ThreadContext
   x86 手工回溯：EBP 链（Game.dll 编译带 frame pointer）
   拿到完整调用栈：[(模块, RVA), ...]

③ 函数边界
   Capstone 反汇编 .text，用 call/jmp 目标 + 函数序言(55 8B EC)切分函数
   生成 rva → function_start 映射（离线，每版本一次）

④ 知识库 v2（案例缓存，不是白名单）
   {
     "module_fp": "sha1:...",          # 版本指纹
     "rva": "0x0050A568",
     "func": "sub_50A4F0",             # 自动生成
     "stack_fp": "a3f9c1",             # 栈顶3帧哈希
     "exception": "0xC0000005",
     "diagnosis": "UnitRemoveAbility(..., 'AHer')",
     "fix": "...",
     "source": "https://...",          # 出处，可审计
     "confidence": 0.9,
     "hits": 128
   }
```

**关键：`rva` 从"主键"降级为"索引之一"，主键是 `(module_fp, stack_fp)`。** 这样即使 RVA 未知，相同崩溃模式仍能聚合。

### P2 — 打通"崩溃 → JASS 函数"（2~3 周，最有差异化的能力）

本项目已有 `engine/memory.py` 的 `get_instance_info()`，能读：
- `inst_ptr + 24` 是否子线程
- `inst_ptr + 40/44` → `CodeStack`（返回地址数组）
- `inst_ptr + 10324` → script 指针 → `code_base`
- `ret_addr - code_base` → **JASS 字节码偏移**

这就是**把崩溃帧翻译成 JASS 函数**的完整原料。缺的只是：

1. 崩溃发生时（或崩溃前 1 秒）抓取所有 `TJassThread` 的 `CodeStack`；
2. 用 `war3map.j` 的**函数表**（YDWE/pjass 编译产物或 `JassDebug.asi` 输出）把 `code_offset` 映射回 `function Trig_XXX_Actions`；
3. 在报告里输出：`崩溃发生在 Trig_DamageSystem_Actions 第 412 行附近`。

> 这一步做完，**"偏移表"的重要性下降 80%**——因为用户真正想要的是"我哪一行写错了"。

### P3 — 运行时探针（替代静态猜测）

静态正则永远算不准泄露。更可靠的是**在游戏内计数**：

```jass
// 由工具自动注入到地图的探针库（约 200 行）
globals
    integer array Probe_Count       // 按 handle 类型计数
    integer array Probe_LastLine    // 最后一次创建的行号
endglobals

function Probe_OnCreate takes integer hType, integer line returns nothing
    set Probe_Count[hType] = Probe_Count[hType] + 1
    set Probe_LastLine[hType] = line
    if Probe_Count[hType] > THRESHOLD then
        call BJDebugMsg("[LEAK] type=" + I2S(hType) + " line=" + I2S(line))
    endif
endfunction
```

配合已有的 `AgentMonitor`（读 `TCDataAllocator` 的 `total/active`），可以做到：
**"第 12 分钟 location 活跃数从 300 涨到 4 万，全部来自 Trig_XXX 第 88 行"** —— 这才是可执行的结论。

### P4 — Reforged / Lua 支持

| 缺口 | 影响 | 方案 |
|---|---|---|
| 只认 MPQ，不认 CASC | Reforged 资源无法读 | 引入 CascLib / `w3x2lni` |

### P5 — 云端从"日志仓库"升级为"崩溃情报"

现状：`crash_reports` 表存 `log_content[:5000]` 原文，`analysis_result` 存一句话。

建议改为：

```
crash_signature   (module_fp, stack_fp)  → 唯一
crash_occurrence  (signature_id, map_name, game_version, count, first_seen, last_seen)
crash_annotation  (signature_id, human_diagnosis, fix, votes)
```

产出物：
- **"本周 Top 20 崩溃指纹"** 榜单（按地图/版本分组）
- **"首次出现的未知崩溃"** 告警 → 自动触发逆向
- 地图作者可见"你的地图崩溃指纹分布"

这才是"全网唯一"的护城河——**数据飞轮**，而不是又一张偏移表。

## 7. 直接回答："是否穷尽了所有崩溃偏移的地址代码？"

**没有。而且不该以"穷尽"为目标。**

三层回答：

**① 数量层：差 2~3 个数量级。**
57 条 vs 10⁴~10⁵ 个潜在崩溃指令点，覆盖率 < 1%。版本覆盖 5/15+，模块覆盖 3/8。1.27b（国内主力之一）零覆盖。

**② 质量层：有假数据、有冲突、有错配。**
3 条占位符 + 客户端/服务端 RVA 漂移 + 跨版本后缀误配 + DMP 分支不查表。**当前状态下"命中"和"未命中"都不可全信。**

**③ 原理层：穷尽在数学上不成立。**
崩溃是"指令×指针状态"的组合，不是有限枚举；堆破坏类问题的崩溃点每次随机。任何静态表的天花板都在个位数百分比。

**替代方案（已在本报告 §6 给出）**：

```
不要问"这个偏移是什么"，要问"这个崩溃的调用栈长什么样"
不要维护"偏移→文案"，要维护"栈指纹→案例"
不要靠人加条目，要靠机器符号化 + 社区标注
```

一句话：**把知识库从"字典"改造成"缓存"，把分析器从"查表"改造成"符号化+聚类"。**
