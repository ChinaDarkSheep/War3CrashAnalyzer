## 1. 新定位

### 1.1 一句话

**玩家装上就能用的"魔兽崩溃翻译器 + 自动转交作者"**：玩家看得懂"是谁的锅、我能做什么"，作者收到的是"按地图聚合、带证据的崩溃清单"。

### 1.2 两类用户，两种诉求

| 用户 | 想知道 | 工具应给出 |
|---|---|---|
| 玩家 | 为什么崩？是我电脑的问题还是地图的问题？我能怎么办？ | 白话结论 + 责任归属 + 可操作建议；一键把信息交给作者 |
| 地图作者 | 我的地图在玩家那里崩了多少次？崩在哪？是哪类代码引起的？ | 按地图聚合的崩溃指纹排行、样本日志、对应的可疑 JASS 调用位置 |

### 1.3 结论"责任归属"三分法（玩家视角的核心输出）

| 归属 | 典型证据 | 给玩家的建议 |
|---|---|---|
| **地图问题** → 自动转交作者 | Game.dll 内崩溃、栈指纹命中脚本类已知案例 | "已自动反馈给作者，可附上诊断包到作者群" |
| **本机/平台环境问题** → 玩家可自行处理 | 栈顶在显卡驱动（`nvd3dum.dll` 等）、输入法、平台插件（`azurewrath.dll`、`yd_*`、`kk*`）；文件读取损坏 | 更新驱动 / 关闭插件 / 重新下载地图 / 换平台 |
| **编辑器问题**（作者自己的 WE 崩溃） | `Exe: WorldEditKKWE.exe` + 明文原因 | "触发器文件 war3map.wtg 损坏，请用备份恢复" 等 |

### 1.4 范围取舍

- **主打**：1.27a（真实数据 42/42 均为 `1.27.0.52240`）+ 国内生态（KK、YDWE、80 对战）。
- **保留但降级**："作者工具"（静态审计、泄露定位/修复、内存监控）收进次级入口，不作为首页。
- **暂不做**：Reforged / CASC / Lua、注入式游戏内探针、人工大规模扩充偏移表。

## 3. 新发现（旧文档未覆盖）

### 3.1 出货版两大核心功能不可用（最严重）

所有 spec 都打包 `War3SuperAnalyzer.py`，但它运行时 import 了已改结构的 `core/knowledge.py`：

- `War3SuperAnalyzer.py:1378` 按旧的扁平结构 `CRASH_KNOWLEDGE[ver]['offsets']` 取值 → 正则一命中即 `KeyError`，**崩溃诊断不可用**；`:1371` 正则还拼错为 `occured at`。
- `War3SuperAnalyzer.py:528` 使用未定义的 `kernel32` → 每轮 `NameError`，**实时监控不可用**。

### 3.2 真实数据画像（42 份）

| 类别 | 数量 | 当前工具输出 | 应有输出 |
|---|---|---|---|
| Game.dll `0xA08A7` | 16 | 命中"音频"文案（可信度未知） | 指纹聚类 + 标注"待验证" |
| Game.dll 其他已知偏移 | 11 | 命中 | 同上 |
| EIP 无效（`<unknown>`，空函数指针调用） | 4 | "未知偏移 0x00000000" | 回退到下一帧 `Game.dll+0x99449`，并提示栈中有平台插件 `azurewrath.dll` |
| WorldEditKKWE 内存资源不足 | 6 | "Storm.dll 未知偏移" | "编辑器内存不足（32 位进程），建议…" |
| WorldEditKKWE 文件损坏（`war3map.wtg`×3、`war3map.w3a`×2） | 5 | "Storm.dll 未知偏移"，且把 `war3map.w3a` 误识别为地图名 | "触发器/技能数据文件损坏" |

**11 份编辑器崩溃 100% 误诊**，而它们的原因就写在日志明文里（`This application has encountered a critical error:` 下一行 + `File:` 行）。

### 3.3 版本信息被忽略

- 文本日志有 `War3Build: 1.27.0.52240`，代码却遍历所有版本查表。
- dmp 的 `MINIDUMP_MODULE` 内含 `VS_FIXEDFILEINFO`（文件版本号），比 `TimeDateStamp` 更直接；`engine/dmp_parser.py:84` 未读取。
- **暂缓（2026-11-05 决策）**：80 对战使用平台自带的 `plugins\war3\patches\1.27.0\Game.dll`（19 份日志），其布局是否与原版 1.27a 一致需对比两份二进制；当前以 KK 平台与本地客户端为准，该对比不再排期。

### 3.4 地图身份

日志中的地图名多为平台缓存哈希（如 `a3758311aab047f1141639003c484aa7.w3x`）。**待验证假设**：该哈希为地图文件 MD5——若成立，作者用自己地图文件的 MD5 即可认领崩溃数据，这是"转交作者"的天然主键。

### 3.5 其他工程问题

- 打包后 `history.db`、提取结果写入 PyInstaller 临时目录 `_MEIPASS`，退出即丢失。
- 服务端 `server/app.py:221` 直接信任客户端上传的分析结果；无鉴权、无请求体大小限制。
- 上传的日志原文含 Windows 用户名、计算机名、本地路径（按决策保持现状，此处仅作风险记录）。
- `gui/app.py:321` `on_closing` 不读 `min_to_tray`；`gui/tabs/adv_tab.py:129` 使用未 import 的 `Fixer`。
- 单体版修复引擎会把 `CreateTrigger()/CreateTimer()` 的结果也提升并 Destroy，可能删掉地图的触发器/计时器——移植时必须修正。

### 3.6 可行性实验：native 地址表（2026-11-05 用 Capstone 复核）

从本机 1.27a `Game.dll`（13.2 MB，ImageBase `0x6F000000`，SizeOfImage `0xCD8000`）按 `push 签名 / mov edx,名称 / mov ecx,函数 / call` 模式**自动提取出 1291 个 JASS native 名称到实现的映射**（Capstone 复核：调用点均为 `E8 rel32`，名称串在 `.rdata`，实现指针全部落在 `.text`）。

- **同一个名称在文件中有两组注册块**：前一组是真实实现（如 `GroupEnumUnitsInRange → 0x6F1E6960`、`TimerStart → 0x6F1F8FE0`、`RemoveLocation → 0x6F1F2D80`），后一组全部指向 `0x6F70A0C0`（`xor eax,eax; ret` 空实现）。按文件顺序扫描时后一组会覆盖前一组，必须过滤 stub 才能得到真实地址；1291 个名称各有唯一实现。
- **函数边界**：`.text` 中 `CC` 填充段 101,025 处，取每段之后的地址作为函数起点（扫描约 0.2 s），与 native 入口合并后共 101,155 个分段起点；对真实崩溃帧做 Capstone 线性反汇编可确认地址落在指令边界内。
- **31 份真实 1.27a dump**（SizeOfImage 与本机 Game.dll 完全一致）回测 503 个 Game.dll 栈帧：
  - 503/503 落在 `.text` 内，偏移归一正确；
  - 只有 **4 帧（0.8%）** 落在 native 函数体内；
  - 从 native 入口做 3 层直接调用图可达性（5.1 s）覆盖 46 帧（9.1%），但单个引擎函数常被 10+ 个 native 共同可达，无法唯一定位；
  - 31 个崩溃点中 **0 个**落在 native 函数体，3 个能在所属函数内找到字符串线索。
- **字符串线索**（线性反汇编函数体，收集指向 `.rdata` 的立即数）：107/503 帧（21.3%）可拿到至少一条字符串，覆盖 25/31 份 dump；但 22 种字符串里多为 `CFrame.cpp`、`Engine %x`、`delete`、`Misc`、`Net::EVENT_*` 等内部噪音，仅 `Script function timeout!`、`CPlayerWar3.cpp`、`FloatProp.cpp` 等少数有诊断价值。

**结论：不把 native 映射纳入诊断结论。** native 函数体只占崩溃帧的 0.8%，调用图可达性歧义大，硬做会引入误判；函数边界 + 字符串线索可覆盖 21% 帧，但多数为内部噪音，未达到独立功能的价值，暂不实现。若后续要做"作者向"深度报告，可把函数起点与字符串线索放进诊断包（仅本地、不上传），而不是写进四行结论。

### 3.7 JassDebug.asi 崩溃弹窗机制（2026-11-05 静态反汇编）

本机 `C:\war3Dev\JassDebug.asi`（116,224 字节，编译于 2016-12-26，ImageBase `0x10000000`）只依赖 `MessageBoxA` 与 `SetUnhandledExceptionFilter`。

- **加载方式**：TLS 回调 `0x10002A40` 在进程启动时调用 `SetUnhandledExceptionFilter(0x10002310)`，并把原过滤器（游戏自身的崩溃处理）保存到 `[0x1001D1E0]`。**不需要向地图或进程注入任何东西**，ASI 被加载即生效。
- **触发条件**：任意未处理异常（访问违例、除零等）。过滤器先尝试从异常上下文解析 JASS 虚拟机状态（判据为 `[ecx+0x44] == 0x493E0`，即 300000 步数上限），成功则反解崩溃点附近的 JASS 字节码，用 `MessageBoxA` 弹出标题为「调试输出」的窗口：
  - 正常：JASS 伪代码行（定义函数 / 声明局部变量 / 调用 JASS 函数 / 算术逻辑…）+ `\n上级函数为%s` + `\nJASS代码起始地址为%X，JASS代码偏移为%X`；
  - 解析失败：`非JASS语句错误(未知错误)`。
- **弹窗之后**：把 `EXCEPTION_POINTERS` 交给保存的原过滤器，游戏照常写 `Errors\*.dmp` / `*.txt`，弹窗不会阻止原有日志落盘。
- **字符串不是混淆的**：`.rdata` 中全部为 GBK 明文（此前"字符串已混淆、静态不可读"的判断作废）。
- **版本风险**：`[ecx+0x44]` 是版本相关偏移，本机 1.27a 上是否仍成立需实测；若不成立只会退化为"未知错误"文案，不影响崩溃日志。
- **获取样本的正确做法**：复制一张测试地图 → 加触发器 → 在可控时机制造异常 → 本地客户端运行（不是 KK/网易）→ 截图弹窗，或由外部程序读取窗口文本。不需要改游戏进程。
  - 1.27a 的空句柄 native（`GroupEnumUnitsInRange` / `TimerStart` / `TriggerEvaluate` / `RemoveLocation` 等）都有判空保护，靠空对象触发不可靠；用整数除零更确定：把全局整数先设为 0，再 `set udg_X = 1 / udg_Zero`（不要写成字面量 `1/0`，避免编译期报错/折叠）。
  - 弹窗文字可能很长且被截断，截图只能拿到可见部分；后续可加只读的外部抓取（`EnumWindows` + `SendMessage(WM_GETTEXT)`），不注入进程。
- **为什么"制造 JASS 错误"不一定弹窗**（2026-11-05 补充）：
  - 整数除零不产生 CPU 异常：本机 1.27a 实测 `set udg_Temp = 1 / udg_Zero` 正常继续执行，不崩溃；
  - 死循环也不产生未处理异常：Game.dll 的脚本执行器以 `0x493E0`（300000）为步数上限，超限返回码 2，由 Game.dll 打印 `Script function timeout!` 并结束线程（反汇编 `0x6F1BFB48` 的 `push 0x493E0` 与 `0x6F1BFB5C` 的返回码判断）；
  - 因此弹窗只会在真正的访问违例等未处理异常时出现，JASS 层的错误不会触发。
- **过滤器可能被游戏覆盖（本机 KKWE 环境）**：JassDebug 只调用 KERNEL32 的 `SetUnhandledExceptionFilter`；而 `War3.exe` 导入 MSVCR120 的 `__crtSetUnhandledExceptionFilter`，`Game.dll` 导入 `__crtUnhandledException` / `__CppXcptFilter`。若 CRT/游戏在 ASI 之后安装顶层过滤器，JassDebug 的过滤器会被覆盖，表现为"真崩溃、有 Errors 日志、但没有弹窗"（本机 2026-11-04 的两次真实 AV 日志即为此类）。验证时需要让 ASI 晚于游戏初始化加载（本地离线注入或延迟加载），联机环境禁止使用。

### 3.8 `0xA08A7` 根因：CFrame.cpp 的帧上下文注册（2026-11-05）

- **崩溃指令**：`0x6F0A08A7` 为 `cmp dword ptr [esi+8], 0`，崩溃时 `ESI=0`；所属函数 `0x6F0A08A0` 是链表拼接/查找，字符串线索指向 `CFrame.cpp`（`TSExplicitList<CONTEXTHASHOBJ/FRAMEREGHASH>`）。
- **调用链**：`0x6F0A08A0` ← `0x6F09EFB1`（帧/上下文哈希注册）← `0x6F0A01D0`。后者在 `[context+0x24] == -1`（上下文已结束/未初始化）时返回空，调用方未判空直接传入，随后读取 `[0x8]`。
- **上层栈**：稳定为 `0x9EFB6 → (0x981BD ↔ 0xA187E) ×3 → 0x1C10DF / 0x1C0CDE / 0x1CD212（Net::GAMESETUP_WAR3_0003::SLOT）→ 0x5EB79 / 0x5E8C3 / 0x5D721 → War3.exe main`，属于游戏房间/槽位 UI 帧的注册与回收路径。
- **统计**：31 份真实游戏崩溃中 16 份（约 52%）为该签名，调用栈逐帧一致，覆盖 6 张地图（WorldEditTestMap 与 5 张 `maps\yk\*.w3x`），日志版本全部为 1.27.0.52240、且均为 12 名玩家。**不是某张地图的脚本问题。**
- **知识库更正**：原条目（音频句柄溢出）与 `disputed` 中两条音频说法均无依据，已删除；改为 `source` 为 `static/2026-11-05`、`verified` 为 `true` 的引擎 UI 帧条目，归属「暂无法确定」，建议改为复现/收集日志而非“按偏移找地图作者”。`core/diagnosis.py` 支持条目级 `attribution` / `suggestion` 覆盖，未提供时仍按原逻辑归为「地图」。
- **后续可做**：若同一地图在关闭平台插件、单机复现后仍稳定出现，可考虑在诊断包中附带 `Net::GAMESETUP_WAR3_0003` 帧链说明；不做自动改判。

### 5.3 许可证边界（发行前必须确认）

- **可并入闭源发行版**：MIT（minidump、War3Net、StormLib、CascLib、rust-minidump）、BSD-2（pjass）、Unlicense。
- **只能外部进程调用或仅作参考**：GPL-3.0（w3x2lni、YDWE、WarcraftHelper）、AGPL-3.0（HiveWE）。
- 现有做法已经是"外部 exe 调用"（`MPQEditor.exe`），pjass / w3x2lni / minidump-stackwalk 可沿用同一模式，不动许可证边界。

### 5.4 核实但仍缺的环节

- **崩溃帧 → JASS 函数**：社区公开材料里仍没有现成开源实现（俄社区的 JassSpy / war3log 无公开源码仓库）。P3.1 已验证"native 地址表 + 函数边界"路线：地址表可自动生成，但崩溃帧只有 0.8% 落在 native 函数体内，无法据此反推 JASS 函数；该方向关闭，除非拿到平台 patch 版的符号或差异化样本。
- **地图哈希 → 作者认领**：没有任何现成项目做这件事，需要自建（P2.2/P2.3）。
- **native 函数签名**：`common.j` / `Blizzard.j` 在 [BribeFromTheHive/Blizz-Libraries](https://github.com/BribeFromTheHive/Blizz-Libraries) 等仓库有整理版；War3Net 亦内置。P3.1 需要时以其为签名来源。
