## 1. 新定位

### 1.1 一句话

**玩家装上就能用的"魔兽崩溃翻译器 + 自动转交作者"**：玩家看得懂"是谁的锅、我能做什么"，作者收到的是"按地图聚合、带证据的崩溃清单"。

### 1.2 两类用户，两种诉求

| 用户 | 想知道 | 工具应给出 |
|---|---|---|
| 玩家 | 为什么崩？是我电脑的问题还是地图的问题？我能怎么办？ | 白话结论 + 责任归属 + 可操作建议；一键把信息交给作者 |
| 地图作者 | 我的地图在玩家那里崩了多少次？崩在哪？是哪类代码引起的？ | 按地图聚合的崩溃指纹排行、样本日志、对应的可疑 JASS 调用位置 |

### 1.3 结论"责任归属"三分法（玩家视角的核心输出）

| 归属 | 典型证据 | 给玩家的建议 |
|---|---|---|
| **地图问题** → 自动转交作者 | Game.dll 内崩溃、栈指纹命中脚本类已知案例 | "已自动反馈给作者，可附上诊断包到作者群" |
| **本机/平台环境问题** → 玩家可自行处理 | 栈顶在显卡驱动（`nvd3dum.dll` 等）、输入法、平台插件（`azurewrath.dll`、`yd_*`、`kk*`）；文件读取损坏 | 更新驱动 / 关闭插件 / 重新下载地图 / 换平台 |
| **编辑器问题**（作者自己的 WE 崩溃） | `Exe: WorldEditKKWE.exe` + 明文原因 | "触发器文件 war3map.wtg 损坏，请用备份恢复" 等 |

### 1.4 范围取舍

- **主打**：1.27a（真实数据 42/42 均为 `1.27.0.52240`）+ 国内生态（KK、YDWE、80 对战）。
- **保留但降级**："作者工具"（静态审计、泄露定位/修复、内存监控）收进次级入口，不作为首页。
- **暂不做**：Reforged / CASC / Lua、注入式游戏内探针、人工大规模扩充偏移表。

## 2. 对旧文档的勘误（均已在本机复现）

| 旧文档结论 | 核实结果 |
|---|---|
| §4.1 `reporter.py:80` 解包必崩 | **已不存在**。当前代码已按 5 元组解包。 |
| §4.2 客户端/服务端 RVA 漂移（`0x46394` vs `0x45394`） | **不是漂移**。客户端存 RVA，服务端存节偏移，两者恰差 `0x1000`，指的是同一地址。**真正问题是同一地址两边解释互相矛盾**（`0xA08A7`：客户端"音频句柄溢出" / 服务端"采样率非 44.1kHz"；`0x46394`：客户端"闪电效果" / 服务端"单位选择 UI 渲染"）——说明这些文案多为推测、未经逆向验证。 |
| §3.4 history.db 实证"DMP 不查表导致空白" | **证据不成立**。用当前代码重跑 31 份 Game.dll 崩溃，凡知识库有的偏移 **全部命中**；history.db 中的空白是条目补录前的旧记录。DMP 分支不查表属实，但被文本分支兜底，影响小。 |
| §3.2 `+0x1000` 对 `.rdata` 虚表崩溃错位 | **影响很小**。崩溃 EIP 几乎总在代码段（`0001` 节），本机 Game.dll 的 `.text` VirtualAddress 正是 `0x1000`。读 PE 节表属锦上添花。 |
| §5.3 `engine/memory.py` 是"全项目最有价值部分" | **已重写（P3.3）**。旧实现依赖全内存启发式扫描（36~61 秒/次）并返回过不可能值；现改为读取已实测的固定锚点，单次约 14 ms，详见 §3.10。 |
| §2.2 占位符假数据 3 条 | **实际至少 5 条**：另有 1.27a 的 `0x0055AA11`、`0x0022BB33`；且 `0x0050A568`/`0x0050B568` 文案完全重复。 |

旧文档中**成立**的结论：跨版本"后 5 位后缀匹配"（`core/auditor.py:380`）、`fixer.py` 顶层 `import openai` 且用已下线模型、`adv_tab.py` 中同步审计/实时终端/退出补丁为假实现、spec 缺 `listfiles`。

## 3. 新发现（旧文档未覆盖）

### 3.1 出货版两大核心功能不可用（最严重）

所有 spec 都打包 `War3SuperAnalyzer.py`，但它运行时 import 了已改结构的 `core/knowledge.py`：

- `War3SuperAnalyzer.py:1378` 按旧的扁平结构 `CRASH_KNOWLEDGE[ver]['offsets']` 取值 → 正则一命中即 `KeyError`，**崩溃诊断不可用**；`:1371` 正则还拼错为 `occured at`。
- `War3SuperAnalyzer.py:528` 使用未定义的 `kernel32` → 每轮 `NameError`，**实时监控不可用**。

### 3.2 真实数据画像（42 份）

| 类别 | 数量 | 当前工具输出 | 应有输出 |
|---|---|---|---|
| Game.dll `0xA08A7` | 16 | 命中"音频"文案（可信度未知） | 指纹聚类 + 标注"待验证" |
| Game.dll 其他已知偏移 | 11 | 命中 | 同上 |
| EIP 无效（`<unknown>`，空函数指针调用） | 4 | "未知偏移 0x00000000" | 回退到下一帧 `Game.dll+0x99449`，并提示栈中有平台插件 `azurewrath.dll` |
| WorldEditKKWE 内存资源不足 | 6 | "Storm.dll 未知偏移" | "编辑器内存不足（32 位进程），建议…" |
| WorldEditKKWE 文件损坏（`war3map.wtg`×3、`war3map.w3a`×2） | 5 | "Storm.dll 未知偏移"，且把 `war3map.w3a` 误识别为地图名 | "触发器/技能数据文件损坏" |

**11 份编辑器崩溃 100% 误诊**，而它们的原因就写在日志明文里（`This application has encountered a critical error:` 下一行 + `File:` 行）。

### 3.3 版本信息被忽略

- 文本日志有 `War3Build: 1.27.0.52240`，代码却遍历所有版本查表。
- dmp 的 `MINIDUMP_MODULE` 内含 `VS_FIXEDFILEINFO`（文件版本号），比 `TimeDateStamp` 更直接；`engine/dmp_parser.py:84` 未读取。
- **暂缓（2026-11-05 决策）**：80 对战使用平台自带的 `plugins\war3\patches\1.27.0\Game.dll`（19 份日志），其布局是否与原版 1.27a 一致需对比两份二进制；当前以 KK 平台与本地客户端为准，该对比不再排期。

### 3.4 地图身份

日志中的地图名多为平台缓存哈希（如 `a3758311aab047f1141639003c484aa7.w3x`）。**待验证假设**：该哈希为地图文件 MD5——若成立，作者用自己地图文件的 MD5 即可认领崩溃数据，这是"转交作者"的天然主键。

### 3.5 其他工程问题

- 打包后 `history.db`、提取结果写入 PyInstaller 临时目录 `_MEIPASS`，退出即丢失。
- 服务端 `server/app.py:221` 直接信任客户端上传的分析结果；无鉴权、无请求体大小限制。
- 上传的日志原文含 Windows 用户名、计算机名、本地路径（按决策保持现状，此处仅作风险记录）。
- `gui/app.py:321` `on_closing` 不读 `min_to_tray`；`gui/tabs/adv_tab.py:129` 使用未 import 的 `Fixer`。
- 单体版修复引擎会把 `CreateTrigger()/CreateTimer()` 的结果也提升并 Destroy，可能删掉地图的触发器/计时器——移植时必须修正。

### 3.6 可行性实验：native 地址表（2026-11-05 用 Capstone 复核）

从本机 1.27a `Game.dll`（13.2 MB，ImageBase `0x6F000000`，SizeOfImage `0xCD8000`）按 `push 签名 / mov edx,名称 / mov ecx,函数 / call` 模式**自动提取出 1291 个 JASS native 名称到实现的映射**（Capstone 复核：调用点均为 `E8 rel32`，名称串在 `.rdata`，实现指针全部落在 `.text`）。

- **同一个名称在文件中有两组注册块**：前一组是真实实现（如 `GroupEnumUnitsInRange → 0x6F1E6960`、`TimerStart → 0x6F1F8FE0`、`RemoveLocation → 0x6F1F2D80`），后一组全部指向 `0x6F70A0C0`（`xor eax,eax; ret` 空实现）。按文件顺序扫描时后一组会覆盖前一组，必须过滤 stub 才能得到真实地址；1291 个名称各有唯一实现。
- **函数边界**：`.text` 中 `CC` 填充段 101,025 处，取每段之后的地址作为函数起点（扫描约 0.2 s），与 native 入口合并后共 101,155 个分段起点；对真实崩溃帧做 Capstone 线性反汇编可确认地址落在指令边界内。
- **31 份真实 1.27a dump**（SizeOfImage 与本机 Game.dll 完全一致）回测 503 个 Game.dll 栈帧：
  - 503/503 落在 `.text` 内，偏移归一正确；
  - 只有 **4 帧（0.8%）** 落在 native 函数体内；
  - 从 native 入口做 3 层直接调用图可达性（5.1 s）覆盖 46 帧（9.1%），但单个引擎函数常被 10+ 个 native 共同可达，无法唯一定位；
  - 31 个崩溃点中 **0 个**落在 native 函数体，3 个能在所属函数内找到字符串线索。
- **字符串线索**（线性反汇编函数体，收集指向 `.rdata` 的立即数）：107/503 帧（21.3%）可拿到至少一条字符串，覆盖 25/31 份 dump；但 22 种字符串里多为 `CFrame.cpp`、`Engine %x`、`delete`、`Misc`、`Net::EVENT_*` 等内部噪音，仅 `Script function timeout!`、`CPlayerWar3.cpp`、`FloatProp.cpp` 等少数有诊断价值。

**结论：不把 native 映射纳入诊断结论。** native 函数体只占崩溃帧的 0.8%，调用图可达性歧义大，硬做会引入误判；函数边界 + 字符串线索可覆盖 21% 帧，但多数为内部噪音，未达到独立功能的价值，暂不实现。若后续要做"作者向"深度报告，可把函数起点与字符串线索放进诊断包（仅本地、不上传），而不是写进四行结论。

### 3.7 JassDebug.asi 崩溃弹窗机制（2026-11-05 静态反汇编）

本机 `C:\war3Dev\JassDebug.asi`（116,224 字节，编译于 2016-12-26，ImageBase `0x10000000`）只依赖 `MessageBoxA` 与 `SetUnhandledExceptionFilter`。

- **加载方式**：TLS 回调 `0x10002A40` 在进程启动时调用 `SetUnhandledExceptionFilter(0x10002310)`，并把原过滤器（游戏自身的崩溃处理）保存到 `[0x1001D1E0]`。**不需要向地图或进程注入任何东西**，ASI 被加载即生效。
- **触发条件**：任意未处理异常（访问违例、除零等）。过滤器先尝试从异常上下文解析 JASS 虚拟机状态（判据为 `[ecx+0x44] == 0x493E0`，即 300000 步数上限），成功则反解崩溃点附近的 JASS 字节码，用 `MessageBoxA` 弹出标题为「调试输出」的窗口：
  - 正常：JASS 伪代码行（定义函数 / 声明局部变量 / 调用 JASS 函数 / 算术逻辑…）+ `\n上级函数为%s` + `\nJASS代码起始地址为%X，JASS代码偏移为%X`；
  - 解析失败：`非JASS语句错误(未知错误)`。
- **弹窗之后**：把 `EXCEPTION_POINTERS` 交给保存的原过滤器，游戏照常写 `Errors\*.dmp` / `*.txt`，弹窗不会阻止原有日志落盘。
- **字符串不是混淆的**：`.rdata` 中全部为 GBK 明文（此前"字符串已混淆、静态不可读"的判断作废）。
- **版本风险**：`[ecx+0x44]` 是版本相关偏移，本机 1.27a 上是否仍成立需实测；若不成立只会退化为"未知错误"文案，不影响崩溃日志。
- **获取样本的正确做法**：复制一张测试地图 → 加触发器 → 在可控时机制造异常 → 本地客户端运行（不是 KK/网易）→ 截图弹窗，或由外部程序读取窗口文本。不需要改游戏进程。
  - 1.27a 的空句柄 native（`GroupEnumUnitsInRange` / `TimerStart` / `TriggerEvaluate` / `RemoveLocation` 等）都有判空保护，靠空对象触发不可靠；用整数除零更确定：把全局整数先设为 0，再 `set udg_X = 1 / udg_Zero`（不要写成字面量 `1/0`，避免编译期报错/折叠）。
  - 弹窗文字可能很长且被截断，截图只能拿到可见部分；后续可加只读的外部抓取（`EnumWindows` + `SendMessage(WM_GETTEXT)`），不注入进程。
- **为什么"制造 JASS 错误"不一定弹窗**（2026-11-05 补充）：
  - 整数除零不产生 CPU 异常：本机 1.27a 实测 `set udg_Temp = 1 / udg_Zero` 正常继续执行，不崩溃；
  - 死循环也不产生未处理异常：Game.dll 的脚本执行器以 `0x493E0`（300000）为步数上限，超限返回码 2，由 Game.dll 打印 `Script function timeout!` 并结束线程（反汇编 `0x6F1BFB48` 的 `push 0x493E0` 与 `0x6F1BFB5C` 的返回码判断）；
  - 因此弹窗只会在真正的访问违例等未处理异常时出现，JASS 层的错误不会触发。
- **过滤器可能被游戏覆盖（本机 KKWE 环境）**：JassDebug 只调用 KERNEL32 的 `SetUnhandledExceptionFilter`；而 `War3.exe` 导入 MSVCR120 的 `__crtSetUnhandledExceptionFilter`，`Game.dll` 导入 `__crtUnhandledException` / `__CppXcptFilter`。若 CRT/游戏在 ASI 之后安装顶层过滤器，JassDebug 的过滤器会被覆盖，表现为"真崩溃、有 Errors 日志、但没有弹窗"（本机 2026-11-04 的两次真实 AV 日志即为此类）。验证时需要让 ASI 晚于游戏初始化加载（本地离线注入或延迟加载），联机环境禁止使用。

### 3.8 `0xA08A7` 根因：CFrame.cpp 的帧上下文注册（2026-11-05）

- **崩溃指令**：`0x6F0A08A7` 为 `cmp dword ptr [esi+8], 0`，崩溃时 `ESI=0`；所属函数 `0x6F0A08A0` 是链表拼接/查找，字符串线索指向 `CFrame.cpp`（`TSExplicitList<CONTEXTHASHOBJ/FRAMEREGHASH>`）。
- **调用链**：`0x6F0A08A0` ← `0x6F09EFB1`（帧/上下文哈希注册）← `0x6F0A01D0`。后者在 `[context+0x24] == -1`（上下文已结束/未初始化）时返回空，调用方未判空直接传入，随后读取 `[0x8]`。
- **上层栈**：稳定为 `0x9EFB6 → (0x981BD ↔ 0xA187E) ×3 → 0x1C10DF / 0x1C0CDE / 0x1CD212（Net::GAMESETUP_WAR3_0003::SLOT）→ 0x5EB79 / 0x5E8C3 / 0x5D721 → War3.exe main`，属于游戏房间/槽位 UI 帧的注册与回收路径。
- **统计**：31 份真实游戏崩溃中 16 份（约 52%）为该签名，调用栈逐帧一致，覆盖 6 张地图（WorldEditTestMap 与 5 张 `maps\yk\*.w3x`），日志版本全部为 1.27.0.52240、且均为 12 名玩家。**不是某张地图的脚本问题。**
- **知识库更正**：原条目（音频句柄溢出）与 `disputed` 中两条音频说法均无依据，已删除；改为 `source` 为 `static/2026-11-05`、`verified` 为 `true` 的引擎 UI 帧条目，归属「暂无法确定」，建议改为复现/收集日志而非“按偏移找地图作者”。`core/diagnosis.py` 支持条目级 `attribution` / `suggestion` 覆盖，未提供时仍按原逻辑归为「地图」。
- **后续可做**：若同一地图在关闭平台插件、单机复现后仍稳定出现，可考虑在诊断包中附带 `Net::GAMESETUP_WAR3_0003` 帧链说明；不做自动改判。

### 3.9 `0x99449`：CFrame 渲染时使用了已释放的帧对象（次高频，2026-11-05）

- **崩溃形态**：异常地址是野指针（`0x017B000A` 一类），调用栈首个有效帧为 `Game.dll+0x99449`；该指令位于帧渲染方法 `0x6F099210` 内，紧随 `call dword ptr [edx+0x2c]`（`0x6F099446`，`edx = [edi]` 即对象的虚表指针）。说明帧对象的虚表槽已指向垃圾地址，对象在释放后仍被渲染。
- **函数语义**：`0x6F099210` 使用栈 Cookie，做矩形/缩放变换后调用全局渲染器 `0x6F0E3980`（转发 6 个 float 到渲染器虚表 `+0x48`），再走 `+0x2c/+0x30/+0x34` 三个虚函数，并按 `[edi+0x1c]` 遍历子帧调用 `+0x24`；属于 `CFrame` 的渲染/更新循环。
- **调用链**：`0x99449` ← `0x9947D` ← `0x9BF2C`（主 UI 根帧 `[0x6FBB9D88]` 的虚函数 `+0x24` 更新）← `0x17587B`（间接回调返回点）← `azurewrath.dll+0x2E361`。4 份样本均为 80 平台客户端（加载 `azurewrath.dll`），KK 环境尚无同类样本。
- **统计**：31 份真实游戏崩溃中 4 份为该签名，涉及 2 张地图；崩溃地址本身无效，之前只能按“首个有效帧未收录”给出 26% 的「地图」猜测。
- **知识库处理**：新增 `0x99449` 条目（置信度 0.6、`verified: true`），归属「本机环境或对战平台」，建议单机复现并在平台侧排查；不再把这类引擎 UI 生命周期崩溃推给地图作者。

### 3.10 `engine/memory.py` 实时监控实测与重写（2026-11-05，P3.3）

**实测环境**：本机 1.27a（`1.27.0.52240`），直接启动 `C:\war3Dev\War3.exe` 并进入自带 1v1 对战地图；`Game.dll` 运行时基址 `0x6A350000`（ImageBase `0x6F000000`，ASLR 生效）。

**已验证锚点链**（以下均为 Game.dll 模块 RVA）：

|---|---|---|

**JASS 线程列表暂不支持**：1.27a 中 `CAgentGenerator` / `JassThreadLocal` 是函数内静态类，`.data` 只有类名字符串，没有 COL/vtable 引用，无法定位其全局实例；旧 `get_instance_info()` 输出的调用栈 / opcode 从未被验证。已删除该能力，界面明确显示"1.27a 暂不支持读取 JASS 线程列表"，不再伪造线程状态。

### 3.12 `0x2651E4`：`Player(16)` / `GetLocalPlayer` 玩家槽越界（2026-11-05）

**地址换算**：日志中的 `Logical addr` 为 `0001:002641E4`，按 `.text` 虚拟地址 `0x1000` 换算后真实 RVA 为 `0x2651E4`（与 `0x50B568` 同一换算规则）。

**崩溃现场**：`0x2651E4` 是 `mov esi, dword ptr [ebx+0x10]`。3 份真实 dump 的寄存器完全一致：`EBX=ESI=0x10`，即访问 `0x20` 触发访问违规，与日志 `referenced memory at 0x00000020` 吻合。所属函数 `0x2651D0` 是 CGameState（`this=EDI`）的句柄/对象注册方法：使用句柄表 `+0x194`（容量）/`+0x198`（活动数）/`+0x19C`（基址，步长 12）、free list `+0x184/+0x188/+0x18C` 与哈希表 `+0x1C0/+0x1C8`；入口 `test ebx,ebx / je` 只判空，**不校验对象指针是否有效**。

**对象来源与数组边界**：

- `0x1C3330` 为 `mov eax,[ecx+eax*4+0x58]; ret 4`；调用方以 `ecx=[0x6FBE4238]` 传入 CGameWar3 单例，即按索引读取 `CGameWar3+0x58+index*4` 的玩家槽指针。`0x1C3200` 另返回 `[CGameWar3+0x1C]` 的 CGameState，作为 `0x2651D0` 的 this。
- CGameWar3 主构造函数 `0x1BD5F0` 在 `0x1BD7C2` 以 `push 0x10; push 4; lea eax,[esi+0x58]; call 0x771B16` 初始化 **16 项 × 4 字节**数组（`+0x58..+0x97`）；`0x1BD7AE` 先构造紧随其后的 `+0x98` 成员。索引 16 会越界读到该成员的首 dword，三份 dump 中它恰好为 `0x10`。

**native 身份**：Game.dll 的 native 注册序列为 `push <签名串VA>; mov edx,<名称串VA>; mov ecx,<函数VA>; call 0x7E3710`。据此在 `0x1ECA4D` 附近解出：

- `0x1F1E70` = JASS native **`Player(integer)`**，签名 `(I)Hplayer;`
- `0x1E3150` = JASS native **`GetLocalPlayer()`**，签名 `()Hplayer;`

两者都经 `0x1C3330 → CGameState → 0x2651D0` 注册玩家句柄，说明该崩溃点是"把玩家对象交给引擎登记"的公共路径。

**三份真实样本**：

| 日志 | 地图 | Game.dll 基址 / EIP | 关键寄存器 | 上层调用 | 栈指纹 |
|---|---|---|---|---|---|
| 2026-10-24 19.15.05 | `a3758311…w3x` | `0x7B770000` / `0x7B9D51E4` | `EBX=ESI=0x10`，`EDI=ECX=EAX=0x157F27B4` | `0x2651E4 ← 0x1E3191 ← War3API.dll#0004:F2E6` | `83A3D323A440` |
| 2026-10-31 18.30.25 | `83f5983b…w3x` | `0x52C50000` / `0x52EB51E4` | `EDI=EAX=0x172227B4`，`[ebp+8]=0x10` | `0x2651E4 ← 0x1F1E99`（`Player`）`← 0x7EF6E3`（脚本间接调用） | `2413B05B6F28` |
| 2026-10-31 18.36.00 | 同上 | 同上 | `EDI=0x178D27B4`，`EBX=ESI=0x10` | 同上 | `2413B05B6F28` |

第 2、3 份由地图脚本把 `16` 传给 `Player(integer)`，属于脚本越界；第 1 份由第三方 `War3API.dll` 调用 `GetLocalPlayer()` 进入同一路径，崩溃时本地玩家槽同样无效。两条路径的栈指纹不同，可用于区分脚本侧与插件侧。

**旧文案证伪**：知识库原条目称"单位组枚举 (GroupEnum) 崩溃 / 枚举中删除单位"，但 42 份日志与 3 份 dump 中没有任何单位组相关帧；崩溃指令与 `GroupEnum*` 函数无关。该说法已删除。

**知识库处理**：`0x002651E4` 改为 `source=static/2026-11-05`、`confidence=0.8`、`verified=true`、归属「地图」，并删除原 `apis` 中的 10 个 `GroupEnum*`（避免作者工具把成百上千个正常单位组调用列为嫌疑）；建议文案指向"检查 `Player(16)` 与上限写成 16 的循环"，并提示装有 `War3API.dll` 等第三方 JASS 插件时先关闭复现。`War3API.dll` 不是崩溃焦点模块，暂未加入环境识别的归属规则。

**解析缺陷修复**：原 `_loaded_module_tokens` 在 `Loaded Modules` 表头后的第一根分隔线处直接 `break`，导致真实日志的模块列表从未被读取（此前只能看到调用栈里的模块）。现改为跳过段首分隔线、仅在已有记录后遇分隔线才结束，并保留完整路径用于归属判定；`in_stack` 仍区分「加载过」与「调用栈内」。

### 3.16 1.27a 三条 legacy 偏移的静态复核（2026-11-06，P3.11）

**背景**：1.27a 知识库剩余 3 条 `source=legacy`、`confidence=0.4` 的未验证条目：`0x00084510`（旧称多面板刷新）、`0x001E35E0`（旧称 GroupEnumUnitsInRange 空句柄）、`0x001FE500`（旧称 RemoveLocation 空句柄）。

**方法与校准**：stock 1.27a `Game.dll`（ImageBase `0x6F000000`，`.text` RVA `0x1000`、文件偏移 `0x400`）按 `foff = RVA − 0xC00` 换算，PE 段表校验三个 RVA 均落在 `.text` 内。用 6 条已验证签名校准指令边界：`0x10D793`、`0x50B568`、`0xA08A7`、`0x46394`、`0x18EE95`、`0x17407D` 全部正好是指令起点，说明「日志逻辑地址 + 0x1000 = RVA」与 Capstone 线性反汇编对齐可靠。

**结论**：
- `0x00084510` 是合法指令边界，但语义与旧文案不符：它位于 `CHECKBOXHASHNODE` 的删除析构函数 `0x84490` 收尾——`0x844E9` 调用非删除析构 `0x77F50`，随后 `test byte [ebp+8],1` 决定是否调用 `0x1205CE`（第三个参数是字符串 `"delete"`，即 operator delete），`0x84510` 为 `pop esi`，之后 `mov esp,ebp; pop ebp; ret 4`。类身份由 RTTI 确认：vtable `0x6F959E5C` → `.?AUCHECKBOXHASHNODE@@`；构造函数 `0x84340` 在 `+0x194`/`+0x1A0` 构造两个字符串子对象（vtable 分别为 `.?AVRCString@@`、`.?AVRCStaticString@@`），并置 `+0x48 |= 0x200`。`pop esi` 本身只恢复寄存器，不会触发访存异常；若日志落在此处，只能是栈指针/调用链已被更早的越界写或异常破坏。旧「多面板更新过快」没有任何证据。
- `0x001E35E0` 在 stock 1.27a **不是指令边界**：它落在 `0x1E35DF` 的 2 字节 `jmp 0x1E35FA` 第 2 字节，不可能成为 EIP 或调用栈返回地址。所在函数 `0x1E35C0` 只是一个句柄类型分派器（经 `0x1E5D90` 取类型后与 `0x27`/`0x4C` 比较再分派），与 GroupEnumUnitsInRange 无关；条目连同错误关联的 10 个 `GroupEnum*` API 一并删除，避免作者定位被误导。
- `0x001FE500` 同样不是指令边界：它落在 `0x1FE4FF` 的 `mov dword [edx+4], 0` 第 2 字节。所在函数 `0x1FE4F0` 只初始化一个 12 字节双向链表节点（写 `[ecx]`、`[ecx+4]`、`[ecx+8]` 并修正前后链），与 RemoveLocation 无关，条目删除。
- 交叉核对：检索 `C:\war3Dev\Errors` 的 117 份文本样本（逻辑地址与 `+0x1000` 变体），三条地址均 0 命中；同一检索方式对已验证签名有效（`0xA08A7` 16 份、`0x10D793` 2 份、`0x50B568` 3 份）。「legacy 键少加 0x1000」的假设也不成立：三个 `+0x1000` 目标同样全部落在指令内部。

**结果**：1.27a 条目由 11 条减为 9 条（8 条已验证 + `0x84510` 静态改写），legacy 未验证条目清零。`0x84510` 现提示「删除析构收尾、非独立根因」，并建议优先排查越界写、递归过深或异常跨越析构。42 份真实样本回归：知识库命中仍为 31/42（仅命中 8 条已验证签名），归属分布不变（本机 12 / 地图 8 / 暂无法 21 / 编辑器 1），平台证据 19 份（栈内 6 份）；三条 legacy 地址 0 命中。

### 3.17 原始日志采集上传（2026-11-06，P2.6）

**背景**：自动上报只传派生字段，遇到知识库未收录的崩溃时缺少原始日志与 dump 可供复核；KK 局内中断又常常不产生 `Errors` 文件。需要一条面向玩家的兜底采集路径。

**用户决策**：原始日志保留 **7~15 天**；单次上传上限 **50 MB**；网页上传生成 **6 位上传码**，用于群里报码、防滥用与后续查询分析结果。

**实现**：
- `GET /upload` 提供两个区域：崩溃记录文件夹（可拖入单次崩溃目录，也可拖入整个 `Errors`，按子目录识别多次崩溃）与 KK 会话文件夹；支持文件夹、零散文件与 zip 兜底。
- `POST /api/upload` 接收 `crash` / `kk` 两组 multipart 文件；`crash_paths` / `kk_paths` 保留浏览器的相对目录结构。崩溃区识别 `Crash.txt` / `Error.txt` / `War3Crash.txt` / `Bug.txt`（允许 `2026-10-14 19.11.29 Crash.txt` 这类时间前缀）与 `.dmp` / `.mdmp`；KK 区识别 `platform.log`、`downloader.log`、`war3/<pid>/war3dll.log`。
- 崩溃区从主日志提取 `War3Build`、地图名、模块内偏移与知识库诊断；KK 区提取 `game.dll =` / `war3.exe =` 版本、`wa(660), map:`、`wa(661), path:` 与 32 位地图 MD5，并可识别会话目录时间戳。两者互补：无 Errors 的平台局也能拿到版本与地图身份。
- 服务端按文件内容 SHA-256 去重，重复上传返回原上传码；上传码为 6 位数字，按码查询只返回时间、版本、地图、偏移、诊断摘要与保留状态，不返回原始日志、绝对路径、Windows 用户名或计算机名。
- 限制：50 MB、每区 40 个文件、落盘 120 个文件、扩展名白名单；zip 拒绝加密、符号链接、路径穿越、非白名单条目与解压超限；每 IP 默认每小时 10 次上传、240 次查询。
- 原始文件存放在 `server/uploads/<code>/`（不在静态目录），默认保留 14 天并自动清理；`raw_uploads` 只保留派生元数据，便于到期后仍能按上传码回看结论。

**验证**：Flask 测试客户端覆盖正常崩溃上传（命中 `0x10D793` → 1.27a Game.dll）、重复上传去重、KK GBK 日志解析（地图名 / MD5 / 版本 / 会话）、空上传、非法扩展名、路径穿越、zip 穿越、合法 zip、41 文件超限、上传码查询脱敏、原始文件不可静态访问、到期清理与保留天数收敛，全部通过。

### 5.3 许可证边界（发行前必须确认）

- **可并入闭源发行版**：MIT（minidump、War3Net、StormLib、CascLib、rust-minidump）、BSD-2（pjass）、Unlicense。
- **只能外部进程调用或仅作参考**：GPL-3.0（w3x2lni、YDWE、WarcraftHelper）、AGPL-3.0（HiveWE）。
- 现有做法已经是"外部 exe 调用"（`MPQEditor.exe`），pjass / w3x2lni / minidump-stackwalk 可沿用同一模式，不动许可证边界。

### 5.4 核实但仍缺的环节

- **崩溃帧 → JASS 函数**：社区公开材料里仍没有现成开源实现（俄社区的 JassSpy / war3log 无公开源码仓库）。P3.1 已验证"native 地址表 + 函数边界"路线：地址表可自动生成，但崩溃帧只有 0.8% 落在 native 函数体内，无法据此反推 JASS 函数；该方向关闭，除非拿到平台 patch 版的符号或差异化样本。
- **地图哈希 → 作者认领**：没有任何现成项目做这件事，需要自建（P2.2/P2.3）。
- **native 函数签名**：`common.j` / `Blizzard.j` 在 [BribeFromTheHive/Blizz-Libraries](https://github.com/BribeFromTheHive/Blizz-Libraries) 等仓库有整理版；War3Net 亦内置。P3.1 需要时以其为签名来源。
