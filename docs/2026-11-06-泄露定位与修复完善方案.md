# 客户端泄露定位与修复完善方案（P5）

- 日期：2026-11-06
- 状态：已定稿（6 项决策已确认）；P5.0–P5.6 已完成（2026-11-07）
- 范围：客户端「泄露定位&修复」能力与界面
- 相关代码：`core/leak_catalog.py`、`core/leak_fixer.py`、`core/leak_report.py`、`core/map_script.py`、`gui/tabs/leak_fix_tab.py`
- 定位：面向地图作者的“JASS 泄露体检与分级修复助手”，精度优先，不是“一键修复器”
- 目标：把当前基于正则的启发式扫描，升级为“可解释、可复核、可控修复”的静态分析链路

## 1. 结论摘要

1. **定位**：本功能是作者向的“体检 + 分级修复”，不是“一键修复器”。主用户是新手/中级地图作者；玩家侧只在崩溃报告中获得“疑似泄露证据”，不提供改图入口（线上平台地图由服务端下发，本地改图无效且可能不同步）。
2. **理论边界**：固定程序无法完全修复泄露。原因不是条件嵌套（函数内嵌套可用 CFG + 活跃变量 + 全出口插入解决），而是跨函数逃逸、别名、动态调用、第三方系统语义，以及“生命周期意图只有作者知道”。销毁动作本身带副作用，误修的代价远大于泄露。
3. **精度优先**：只对白盒可证的模式自动修复；其余只给证据和补丁建议。报告必须显式声明覆盖范围，不承诺“修完不再泄露”。
4. **当前实现**能处理点、单位组、矩形等少数类型，但存在控制流、脚本路径、Lua 地图、误报和不可撤销等实质问题，不适合继续在现有结构上叠加规则。
5. **全网没有可直接复用的成熟 Python JASS 泄露自动修复器**。可参考的是 WarRaft 的 Tree-sitter 静态分析、YDWE 的历史泄漏检测、Leak Check/LeakLess 的误报经验，以及 jassdoc/pjass/jassjs 等语法与 API 基础设施。
6. **实施分两阶段**：
   - 第一阶段（P5.0–P5.5）自建 JASS 词法/语法/语义分析，自动修复范围限定为**点、单位组、玩家组**三类 A 级规则，强制 diff、备份、撤销；
   - 第二阶段（P5.6+）扩展到矩形、区域、特效、闪电等类型，以及 Lua 地图。
7. 任何自动修复都必须满足：不覆盖原图、可预览、可撤销、幂等、可通过 pjass（若可用）或重新提取校验。

## 1.1 用户与使用场景

| 用户 | 场景 | 本功能提供 | 本功能不提供 |
| --- | --- | --- | --- |
| 新手/中级作者（主） | 地图长期运行后内存上涨、卡顿、最终崩溃 | 分级泄露清单、证据、修复建议、可预览可撤销的 A 级自动修复 | 不替作者判断生命周期，不承诺修复所有泄露 |
| 进阶作者 | 想快速复核脚本或交给 AI 分析 | 统一报告中的可疑函数完整片段、规则编号、JSON 导出 | 不做全量重写，不改写作者代码风格 |
| 玩家 | 遇到疑似地图导致的崩溃 | 崩溃报告中的“疑似泄露证据”，用于反馈作者 | 不提供改图入口，不改本地地图，不注入线上对局 |

## 2. 现状审计

### 2.1 当前能力

| 能力 | 位置 | 说明 |
| --- | --- | --- |
| 脚本提取 | `Fixer._extract_script` | 通过 MPQEditor 从地图提取 `war3map.j` / `war3map.lua`，支持 listfile 扫描 |
| 泄露定位 | `Fixer.locate_leaks` | 扫描函数顶部局部变量和内联创建调用 |
| 基础修复 | `Fixer.transform_script` / `transform_function_block` | 为局部点、组、矩形补销毁，并提升内联创建 |
| 报告 | `Fixer.generate_ai_report` | 输出疑似函数片段，供 AI 或人工继续分析 |
| 界面 | `gui/tabs/leak_fix_tab.py` | 只提供点、组、矩形、执行优化四个开关，以及定位/修复/报告三个按钮 |

### 2.2 主要问题

| 严重度 | 问题 | 影响 |
| --- | --- | --- |
| 高 | `leak_fix_worker` 无论原脚本是 `war3map.j`、`scripts\war3map.j` 还是 `war3map.lua`，都写回 `war3map.j` | Lua 地图会被写入 JASS 文本而损坏；脚本路径不一致时修复不生效 |
| 高 | 清理代码插入在“第一个包含 return 的行”前 | 若 return 位于某个分支内，其他分支不会执行清理；多 return 只处理第一处 |
| 高 | 没有作用域、引用和逃逸分析 | 变量被传入其他函数、存入全局或哈希表时仍可能被自动销毁，改变地图逻辑 |
| 高 | 没有 diff、备份和撤销 | 作者无法在应用前复核，误改后难以恢复 |
| 高 | 玩家组创建函数包含共享全局对象：`GetPlayersAll()` 返回 `bj_FORCE_ALL_PLAYERS` | 若按类型盲目插入 `DestroyForce`，会破坏游戏全局状态；必须按创建函数白名单区分 |
| 中 | 只用正则匹配，注释和字符串未屏蔽 | 注释里的函数名会误报，字符串中的内容也可能被误改 |
| 中 | 仅修复函数体顶部的点/组/矩形；玩家组虽能定位但不修复；region、effect、lightning、image、texttag、sound 等规则不完整 | 大量真实泄露无法定位或只能定位不能修 |
| 中 | 销毁判断是“函数内出现过 `DestroyXxx(var)` 字符串” | 分支中的销毁被当成全局已处理，产生漏报 |
| 中 | 不区分一次性与长期持有的计时器、触发器、哈希表 | 自动销毁可能破坏地图逻辑；当前用 `NO_AUTO_DESTROY` 简单规避，但缺少解释 |
| 中 | 内联提升可能改变实参求值顺序 | 有副作用的函数调用被提前执行，可能改变行为 |
| 中 | Lua 仅提示“不支持”，但仍继续生成 JASS 修复结果 | 用户容易误以为修复成功 |
| 低 | `generate_ai_report` 把“函数内有创建、无销毁”和“多个 return”都算可疑 | 报告噪声大，难以直接使用 |
| 低 | 没有自动化测试与真实地图语料 | 规则调整无法量化回归 |

结论：现有代码适合作为“规则原型”，但不适合继续堆叠。应先把脚本 IO、词法/语法、语义和修复计划拆开。

### 3.2 泄露类型与清理方式

| 类型 | 常见创建函数 | 清理方式 | 自动修复建议 |
| --- | --- | --- | --- |
| location 点 | `Location`、`GetUnitLoc`、`GetSpellTargetLoc`、`GetRectCenter`、`PolarProjectionBJ` | `RemoveLocation` | 本版 A 级，可自动修复 |
| group 单位组 | `CreateGroup`、`GetUnitsOfPlayerAll`、`GetUnitsInRectAll`、`GetUnitsInRangeOfLocAll` | `DestroyGroup`；GUI 枚举可配合 `bj_wantDestroyGroup = true` | 本版 A 级；GUI 枚举规则需单独识别 |
| force 玩家组 | `CreateForce`、`GetForceOfPlayer`、`GetPlayersMatching` | `DestroyForce` | 本版 A 级，**仅限新建 force**；`GetPlayersAll` 返回共享全局，禁止销毁 |
| rect 矩形 | `Rect`、`RectFromCenterSizeBJ` | `RemoveRect` | 本版 B 级，只给补丁 |
| region 区域 | `CreateRegion` | `RemoveRegion` | 本版 B 级，只给补丁 |
| effect 特效 | `AddSpecialEffect`、`AddSpecialEffectLoc`、`AddSpecialEffectTarget` | `DestroyEffect` | 本版 B 级；持续特效需按生命周期处理 |
| lightning 闪电 | `AddLightning`、`AddLightningEx` | `DestroyLightning` | 本版 B 级 |
| image 图像 | `CreateImage` | `DestroyImage` | 中置信，需确认生命周期 |
| ubersplat 地面纹理 | `CreateUbersplat` | `DestroyUbersplat` | 中置信，需确认生命周期 |
| texttag 漂浮文字 | `CreateTextTag` | `DestroyTextTag` | 中置信；可能依赖显示时长 |
| sound 声音 | `CreateSound`、`CreateSoundFilenameWithLabel` | `DestroySound` | 中置信；播放中的声音不能随意销毁 |
| boolexpr | `Condition`、`Filter` | `DestroyBoolExpr` | 中高置信；注意匹配枚举函数的归属 |
| trigger 触发器 | `CreateTrigger` | `DestroyTrigger` | 低置信自动修复；长期触发器不应销毁 |
| timer 计时器 | `CreateTimer` | `DestroyTimer` | 低置信自动修复；周期计时器通常长期持有 |
| hashtable | `InitHashtable` | `FlushParentHashtable` / `FlushChildHashtable` | 低置信自动修复；注意共享表 |
| unit 单位 | `CreateUnit`、`CreateUnitAtLoc` | `RemoveUnit` | 不自动修复；可能是马甲、召唤物或地图原有单位 |
| item 物品 | `CreateItem`、`CreateItemLoc` | `RemoveItem` | 不自动修复；可能是玩家持有物 |
| destructable 可破坏物 | `CreateDestructable` | `RemoveDestructable` | 不自动修复；需按地图逻辑判断 |
| dialog 对话框 | `DialogCreate` | `DialogDestroy` | 需结合界面生命周期 |
| leaderboard / multiboard | `CreateLeaderboard` / `CreateMultiboard` | `DestroyLeaderboard` / `DestroyMultiboard` | 需结合界面生命周期 |
| unitpool / itempool | `CreateUnitPool` / `CreateItemPool` | `DestroyUnitPool` / `DestroyItemPool` | 需结合对象池生命周期 |

说明：
- 上表是规则目录的起点，落地前应使用 `common.j` / `jassdoc` 对每个创建函数、销毁函数和参数类型做二次核对。
- “可自动修复”只表示该类型具备安全修复的潜力，是否真正自动修复仍取决于控制流、逃逸和使用点分析。
- **本版自动修复范围已限定为 location / group / force 三类**；表中 rect、region、effect、lightning 等即使具备潜力，本期也只到 B 级（只给补丁建议）。
- **force 必须按创建函数白名单处理**：`CreateForce`、`GetForceOfPlayer`、`GetPlayersMatching` 等新建对象可自动销毁；`GetPlayersAll()` 返回全局共享的 `bj_FORCE_ALL_PLAYERS`，销毁会破坏游戏状态。凡是返回共享/全局 force 的封装函数，一律在目录中标注并禁止自动修复。
- `set var = null` 只对 agent 派生类型有意义（unit、group、force、timer、trigger、effect 等）；location、rect 等非 agent 句柄只需调用销毁函数。冗余置空不应被当作“已修复”的证据。

### 3.3 社区共识与常见误区

1. JASS 没有垃圾回收。点、组、玩家组、矩形、特效、计时器、触发器、哈希表等句柄对象需要显式销毁；agent 派生类型的局部变量还需要置空（非 agent 句柄只需销毁）。
2. `TriggerSleepAction` 会让局部变量在线程等待期间继续存活；跨等待的清理需要更保守的控制流分析。
3. 长期持有的触发器、计时器、哈希表不应被“看到就销毁”。当前代码用 `NO_AUTO_DESTROY` 规避，但应改为“规则说明 + 生命周期证据”。
4. GUI 的“单位组枚举”通常依赖 `bj_wantDestroyGroup` 或 BJ 包装函数；只检查 `DestroyGroup` 会漏掉大量 GUI 生成的脚本。
5. 老工具的主要问题是误报：变量可能被传入其他函数、在分支内销毁、或在后续逻辑中继续使用。自动修复必须引入作用域、引用和逃逸分析。
6. 修复后地图必须能在本地客户端加载；仅通过正则替换不能证明修复正确。

### 3.4 运行时句柄普查（参考，不收录代码）

社区流传过一份基于 `ConvertFogState` / `LoadXHandle` 的 JASS 句柄普查库：把整数当作句柄 ID，用对应类型的 Load 函数读取，能读到即说明该 ID 当前存活；按类型累加后与阈值比较并打印。它覆盖 destructable、item、unit、effect、trigger、event、triggercondition、triggeraction、timer、timerdialog、multiboard、group、force、rect、region、location 共 16 类，未覆盖 boolexpr、sound、lightning、image、ubersplat、texttag、trackable、dialog、leaderboard、fogmodifier、hashtable 等，可作为规则目录的覆盖对照。

可借鉴的部分：

- 验证局部 agent 变量置空是否真的释放了引用计数——这是静态分析只能推断、无法证实的事；
- 按类型观察存活数量随时间的增长趋势，作为“是否仍在泄露”的实测证据；
- 在本地测试图上做修复前后 A/B 对比。

不可用的部分：

- 不能定位到函数或代码行；
- 单次计数不是快照：每帧只扫一个 ID，数字是跨几十次至数小时扫描的混合值；
- 阈值没有普适性（单位 3000、可破坏物 10000 等对大型 RPG 完全正常），直接报警会产生大量假阳性；
- 必须写入 `war3map.j` 才能运行，属于改图而非只读分析；
- 句柄 ID 基址（经典版本为 `0x100000`）随版本变化，`ConvertFogState` 传入任意整数处于未定义行为边缘，换版本可能取到垃圾值甚至崩溃；
- 该脚本无许可证声明、带作者署名，视为保留所有权利，**不复制代码、不随项目分发**。

结论：只把“运行时普查”作为 P5.6 的可选验收手段写进流程，不进入产品主链路。若将来自研，必须满足：仅作者本地、仅地图副本、debug-only、分帧采样、时间序列 + 增长斜率、启动前校验句柄基址、失败即退出。

## 4. 目标与边界

### 4.1 目标

- **精度优先**：A 级自动修复以“白盒可证”为前提，precision 是硬指标，召回率只作为报告披露项。
- 对 JASS 脚本给出可解释的泄露清单：规则编号、位置、函数、类型、证据、置信度、修复建议、修复级别（A/B/C）。
- 对 A 级模式生成最小 diff，并允许用户逐条选择、预览、应用、撤销；B 级只生成补丁建议。
- 保持原图不变，输出独立副本；记录原脚本路径、编码和导入结果。
- 修复具备幂等性：重复执行不会重复插入销毁代码。
- 报告显式声明覆盖范围（本版支持哪些类型、哪些明确不处理），避免作者误以为“已全部修复”。
- 统一报告包含定位结果、证据与可疑函数完整片段，可直接交给 AI 或人工复核；不再保留独立的 AI 报告入口。
- 玩家侧在崩溃特征指向内存/句柄耗尽时，报告中追加“疑似地图泄露证据”，不提供改图入口。

### 4.2 非目标

- **不承诺“完全修复”**。控制流复杂、跨函数所有权不明确、生命周期由设计决定的场景只报告，不自动修改。
- 本版不自动修复 rect、region、effect、lightning、timer、trigger、hashtable、unit、item、destructable 等类型。
- 不对 Lua 地图做任何写入；只识别并提示能力边界，排到 P5.7。
- 不对 KK、网易等线上平台做任何注入、挂钩或运行时修改。
- 不随项目分发 w3x2lni（GPL-3.0）等外部工具；pjass 仍按现有方式外部调用，有则校验、缺失则标注。
- 不把运行时句柄普查放进玩家路径或默认流程；它只是作者本地的可选验收手段。

### 5.3 分析流水线

```text
地图 -> 提取脚本（记录原始路径/编码）
     -> Lua? 是 -> 只读提示，结束（不写入）
     -> 词法分析
     -> 语法分析（容错）
     -> 作用域与符号表
     -> 使用-定义 / 逃逸分析
     -> 调用图（含回调注册与 ExecuteFunc）
     -> 控制流图（返回路径、循环体、TriggerSleepAction）
     -> 规则匹配
     -> 安全性分级（A/B/C）
     -> 生成最小编辑与 diff
     -> pjass 校验（有则校验，缺失标注“未校验”）
     -> 用户预览/选择
     -> 写回新地图副本（原始脚本路径）
     -> 重新提取校验 + 统一报告
```

关键分析点：

1. 创建点：函数调用返回值、赋值、局部声明初始化、内联实参。
2. 使用点：读取、作为实参、存入全局/数组/哈希表、返回、跨线程。
3. 逃逸：变量被传入未知函数时默认视为逃逸，不自动修复；只读函数由目录标注。
4. 控制流：清理点必须支配所有退出路径，或在循环体每次迭代结束时执行；多 return、`exitwhen`、`TriggerSleepAction` 都需要显式处理。
5. 幂等：已有 `DestroyXxx(var)` 或 `set var = null` 的位置不得重复插入。
6. 编码：保留原脚本 BOM/编码和换行风格；写回前做字节级比对。

### 5.4 规则分级

| 级别 | 规则示例 | 处理方式 |
| --- | --- | --- |
| A 安全自动 | 局部**点 / 单位组 / 新建玩家组**；未逃逸；所有退出路径可插入；未被提前销毁；force 来自新建白名单 | 生成 diff，默认勾选 |
| B 建议补丁 | 矩形、区域、特效、闪电；分支/循环内创建需要提升；存在跨函数传递但可给出补丁 | 生成补丁，用户逐条确认 |
| C 仅报告 | 单位/物品/可破坏物、长期 timer/trigger/hashtable、共享 force、传入未知函数、生命周期由设计决定、Lua | 只给证据和建议，不自动改 |

### 5.5 修复策略

- 只做插入/替换最小编辑，不重新格式化整个函数。
- 局部变量清理：
  - 在支配所有返回路径的位置插入销毁调用；仅 agent 派生类型再补 `set var = null`（location/rect 等非 agent 句柄不需要置空）；
  - 多 return 时，在每个返回前插入，或在统一出口插入；
  - 循环体内创建的对象，在循环体末尾清理，而不是函数末尾。
- 内联创建：
  - 仅对“独立 call 语句中的匿名创建”做提升；
  - 嵌套调用提升时保持从左到右的求值顺序，或只处理无副作用参数；
  - 生成唯一临时变量名，避免与用户变量冲突。
- GUI 单位组：
  - 识别 `bj_wantDestroyGroup` 模式；
  - 对 BJ 枚举函数给出规则说明，不盲目插入 `DestroyGroup`。
- 玩家组：
  - 只有创建函数在 A 级白名单（`CreateForce`、`GetForceOfPlayer`、`GetPlayersMatching`）内才自动修复；
  - `GetPlayersAll()` 等返回共享全局 force 的调用禁止销毁，只报告；
  - 销毁前确认未被注册为长期回调参数或存入全局。
- 不自动销毁：
  - `CreateTrigger`、`CreateTimer`、`InitHashtable` 等默认只报告；
  - 除非能证明对象在函数内创建且未被返回、未存入全局、未注册事件。
- 修复后：
  - 生成独立地图副本 `*_leakfixed.w3x`；
  - 写回原始脚本路径（`war3map.j` 或 `scripts\war3map.j`），不再统一写成 `war3map.j`；
  - 检查 MPQEditor 返回码；
  - 重新提取脚本并与预期修复文本比对；
  - pjass 存在则自动校验，缺失则在报告中标注“未校验”，不阻断出图；
  - 识别为 Lua 脚本时直接拒绝写入，只输出只读提示。

| 原因 | 样本数 | 说明 |

## 7. 界面设计草案

```text
┌────────────────────────────────────────────────────────────┐
│ 地图：[...w3x]  [选择地图]  [开始扫描]  [导出统一报告] [撤销]│
```

5. 所有外部工具调用失败都要显式提示，不吞异常；pjass 缺失只标注，不阻断。

| 1 | 第一版自动修复范围 | **点、单位组、玩家组** | 三类最常见、语义相对清晰；矩形/区域/特效/闪电留到 B 级建议，避免首版精度失控 |
| 2 | 扫描触发方式 | **手动点击「开始扫描」** | 避免切页即扫描造成卡顿和意外等待；大图分析应有明确预期 |
| 3 | pjass 校验 | **有则校验，缺失则标注** | 不阻断新手流程，同时不给虚假的“已验证”安全感 |
| 4 | Lua 地图 | **本期只读提示，不修复** | 没有语料与运行时验证手段，写入风险高；排到 P5.7 |
| 5 | 报告代码片段 | **仅可疑函数完整片段** | 保留上下文与行号，利于人工/AI 复核，体积可控 |
| 6 | AI 报告入口 | **合并进统一报告** | 减少按钮与重复逻辑；一份报告同时覆盖定位、证据和 AI 片段 |

### 补充约束

- 玩家组自动修复必须以创建函数白名单为准：`CreateForce`、`GetForceOfPlayer`、`GetPlayersMatching` 等新建对象可修；`GetPlayersAll()` 返回共享全局，禁止销毁。
- `set var = null` 只对 agent 派生类型有意义，不作为 location/rect 的修复证据。
- 玩家侧只出证据，不提供改图入口；线上平台地图不可本地替换。
